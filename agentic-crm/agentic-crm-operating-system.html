01

Executive recommendation

One page. The rest of the document is the evidence and the build.

The core decision, reframed

You asked whether Claude should get execution access. The audit answers part of it for you: the MoEngage MCP cannot publish or send a campaign at all — drafts are created via API but published only from the MoEngage dashboard Tested. So the real design space is not "should Claude send?" but "how far into building the campaign should Claude go before a human presses publish?" That is a gift: the platform enforces human-in-the-loop at the riskiest step by construction.

Build an Agentic CRM in two separable halves — intelligence and execution — and never conflate them. Claude's intelligence can run far ahead of its execution rights without any architectural rework, which is exactly the property you asked for.

  1. Operate at Autonomy Level 2 today. Claude analyses performance, detects opportunities, sizes audiences, writes copy, and emits a fully-specified Campaign Build Sheet. A CRM operator executes it in MoEngage. This needs zero engineering and can start this week.
  2. Do not rely on the MoEngage MCP as your analytical data layer. Reads for campaign stats, revenue attribution, delivery, and segment sizing are reliable Tested; the free-form analytics engine (behaviour / funnel / retention) is not — it returned "Query execution failed" with no reason on two valid queries Tested. Historical, cross-domain analysis must come from a warehouse.
  3. Build a CRM Intelligence Layer (warehouse-backed) as the source of truth for orders, margins, inventory, returns, COD behaviour, acquisition source and LTV. MoEngage holds none of these reliably; it should be treated as an execution + engagement-measurement system, not an analytics database.
  4. Give Claude scoped write access to create drafts and test-sends — not publish — as the Level-3 step, gated to a fixed library of pre-approved campaign templates. This is safe precisely because publish stays manual.
  5. Keep discounting, brand voice sign-off, and any first-of-its-kind campaign permanently human. Automate the repetitive, reversible, well-measured 80%; keep judgment calls human.

What to build first (30 days): the Build Sheet template + the Experiment & Learning database + a daily read-only performance brief. What not to build yet: anything that lets Claude publish or send; any autonomous budget/discount decisioning. The one MCP problem to escalate to MoEngage: the opaque failure of the analytics query engine.

Why Claude sometimes "can't retrieve MoEngage data"

Your instinct is right, and the failure is specific rather than random. The retrieval problems cluster into a small number of causes:

Failure class 1

The analytics engine fails opaquely

Behaviour/funnel/retention queries pass client-side validation, reach the backend, get a request ID, then return "Query execution failed" with no field named. Nothing tells Claude what to fix, so it looks like "Claude can't access it." This is the biggest single cause and it's server-side.

Failure class 2

Name resolution is silent

Segment/query filters accept a wrong attribute or event name at create time and only fail later in an async count job — with no reason. Display names vs internal names (City vs moe_city, LTV vs t_rev) are a constant trap.

Failure class 3

Hard windows & sizes

All stats capped at 30 days; per-user events capped at 30 days; EMAIL bodies inline huge HTML that blows the context window; large results get truncated to a file. Long-range or bulk questions simply can't be answered in one call.

Failure class 4

Partial / normalised responses

campaign_name/channel come back null; phantom all-zero variation rows appear; a draft's schedule reads back normalised. The data is there but shaped in ways that look like gaps unless you know them.

Escalate to MoEngage

The class-1 analytics-engine failure is the one worth a support ticket. Everything else is worked around by architecture (below). It is also the strongest reason not to make the MCP your analytical brain.

03

Agentic CRM architecture

Seven layers. The load-bearing idea: intelligence sits on a warehouse, execution sits on MoEngage, and a guardrail layer sits between them. Permissions can rise through the execution layer without touching anything above it.

L1
Customer & Commerce Data
Orders, SKUs, margins, inventory, returns, COD/prepaid, payment behaviour, acquisition source, CS tickets, loyalty, campaign-exposure history + MoEngage events.
L2
CRM Intelligence Layer (warehouse + feature store)
A modelled, query-fast source of truth. RFM, LTV, propensities, replenishment clocks, discount-dependence, category affinity — computed here, not in MoEngage.
L3
Claude Analytical Agents
Performance, Behaviour, Opportunity, Experimentation + specialists. Read L2; read MoEngage outcomes via MCP for measurement.
L4
CRM Decision Engine
Turns opportunities into concrete interventions: who × what × when × channel × offer × message, with an impact estimate.
L5
Guardrails / CRM Constitution
Deterministic policy checks: contact caps, discount rules, suppression, brand voice, experiment rules. Nothing passes without clearing this layer.
L6
Action Queue + Human Approval
Build Sheets and (later) drafts queue here with priority, impact and approval state. Auto-approve lane opens only for pre-cleared template classes.
L7
MoEngage Execution + Measurement
Segments, drafts, campaigns, flows. Human publishes. Outcomes flow back to L1/L2 and into the Learning DB.
↑ learnings feed back to L2 & the Learning DB ↑

The key architectural commitment: MoEngage is L7 only. Treating it as L1/L2 (the current default) is what produces the reliability pain — you are asking an engagement platform to be a data warehouse over an unreliable query API.

Recommendation

Target Architecture 3; start as a thin version of Architecture 2. Use the MoEngage MCP for what it's reliably good at — reading campaign/flow outcomes, sizing segments, creating drafts. 05

Agent architecture

Specialised agents, each with a narrow remit, a defined data source, and a defined output. They are prompts + tool scopes + memory — not separate models.

Analytical

CRM Performance Agent

Revenue, CRM-attributed revenue, CTR/CVR, delivery, unsubs, channel & cohort performance, incrementality vs control, cannibalisation. Reads warehouse + MCP campaign/flow stats. Emits the daily/weekly scorecard & anomaly flags.

Analytical

Customer Behaviour Agent

Shifts in purchase frequency, repeat rate, category migration, product affinity, inter-order time, browse/cart behaviour, lapsing, discount dependence, high-LTV emergence. Reads warehouse feature store.

Decisioning

Opportunity Detection Agent

Ranks actionable cohorts: likely repurchasers, replenishment-due, browse/cart abandoners, cross-sell, lapsers, at-risk, price-drop & back-in-stock matches. Outputs a scored opportunity backlog with revenue-at-stake.

Governance

Experimentation Agent

Owns hypothesis, control/treatment, expected impact, success metric, duration, significance, result, learning. Guards against un-powered tests and reading noise as signal. Writes to the Learning DB.

Additional agents you'll need

Copy & Creative Brief Agent

Generates on-brand copy + creative briefs within the brand guardrails; runs personalisation previews. Never ships without brand-voice check.

Guardrail / Policy Agent

Deterministic. Applies the CRM Constitution to every proposed action: caps, suppression, discount limits, margin floors. A hard gate, not an LLM opinion.

Audience Builder Agent

Resolves cohort logic → validated MoEngage segment (name-resolution + deep-validate + count) so downstream execution never hits silent failures.

Channel & Timing Agent

Picks channel by reachability + fatigue + cost + past cohort response; picks send time. Uses the reachability gap (e.g. push 23% vs WhatsApp 97% for Champions).

Inventory & Margin Agent

Injects commercial reality: what's overstocked, what's low-margin, what must not be discounted. Sources from warehouse; vetoes offers that break margin floors.

Orchestrator

Runs the daily loop, sequences the agents, assembles the Action Plan & Build Sheets, manages the Action Queue and memory.

06

The CRM Constitution

Persistent, versioned business rules Claude operates against — so decisions are bounded and auditable, not improvised each day. Stored as machine-readable policy the Guardrail Agent enforces deterministically. Numbers below are placeholders to ratify with the team.

Contact policy

  • Max 1 promotional contact / user / day across all channels.
  • Max 3 WhatsApp / user / week; max 2 push / day; email uncapped but fatigue-scored.
  • Channel priority default: WhatsApp → Push → Email → SMS, overridden by reachability + cost + cohort response.
  • Fatigue suppression: no promo to a user who received ≥N messages with zero opens in M days.
  • Hard suppression lists always excluded (the excl do segment is already applied on live pushes — good).
  • Transactional & service messages never counted against promo caps.
  • Quiet hours: no messages 10pm–8am local unless user-triggered.

Commercial policy

  • Discounts allowed only for defined triggers (lapsing, cart recovery, clearance) — never as a default lever.
  • Max discount X%; any deeper offer requires human sign-off.
  • Margin floor per SKU/category must be respected after discount — Inventory & Margin Agent veto.
  • Full-price-first: high-intent & recent buyers get non-discount messaging by default.
  • Discount-sensitive cohorts get fewer, deliberately-spaced offers to avoid training discount-waiting.
  • Inventory-aware: prioritise overstock/ageing SKUs for promo; protect scarce/hero SKUs.
  • No stacking of automated offers with active site-wide sales without human review.

Brand policy

Voice & creative guardrails

Approved tone (DailyObjects: witty, premium, design-led — see live copy "Just spotted 🔭"); banned language & claims list; required structure (hook · value · single CTA); emoji usage rules; deeplink & UTM conventions (utm_source/medium/campaign) enforced. No creative ships without a brand-voice check.

Experimentation policy

Test discipline

Every non-trivial change needs a hypothesis + control group; minimum sample & power defined before launch; fixed test period; a single primary KPI + guardrail secondaries; significance threshold pre-registered; roll-out only after a win holds. No peeking-and-shipping.

Safety & governance policy

  • Irreversible actions require explicit human approval — the MCP STOP is irreversible; treat it that way.
  • Every proposed action carries an audience-size sanity bound; a campaign above Y recipients always needs human approval regardless of template.
  • All actions logged with rationale, data snapshot, and policy-version for audit.
  • Data-quality gate: if inputs are stale/failed (e.g. catalogue ERROR, analytics query failure), Claude flags and holds rather than guessing.

Autonomy framework & execution-access models

A 0–5 ladder you can climb without re-architecting. The autonomy lives in the execution layer (L6/L7); the intelligence layers don't change as you climb.

0Manual

Human analysis + human execution

Today's baseline for most decisions. Claude not in the loop. Infra: none. Risk: slow, inconsistent, low learning velocity.

1Analyse

Claude analysis

Claude reads performance & behaviour, produces the scorecard & anomaly flags. Human decides everything. Infra: read access + brief. Risk: near-zero.

2Now

Claude recommendations + human execution Operate here

Claude emits fully-specified Build Sheets; operator builds & publishes in MoEngage. Infra: Build Sheet + Learning DB + read MCP. Risk: low (human builds); main risk is bad recommendations → mitigated by measurement.

Prereq to advance: a warehouse-backed intelligence layer + a track record of accurate impact estimates.
390-day

Claude builds drafts + human approves & publishes

Claude uses create_campaign_draft/patch for pre-approved templates; human reviews the draft & publishes (publish is dashboard-only anyway). Infra: scoped write creds, template library, approval queue, read-back diffing. Risk: medium (bad draft) — bounded by mandatory human publish.

Prereq: reliable draft creation with read-back validation; brand & guardrail checks automated; approval UI.
4Later

Claude executes low-risk campaigns semi-autonomously

For a whitelist of small, reversible, well-measured template classes (e.g. cart recovery under a size cap), auto-approval + a human check on STOP/pause. Still bounded by the publish constraint unless a send API is added. Risk: medium-high.

Prereq: months of clean Level-3 audit trail; automated post-send anomaly detection + rollback playbook.
5Aspirational

Claude manages CRM within economic/customer guardrails

Autonomous decisioning, execution, optimisation, pausing & reallocation inside the Constitution; humans supervise exceptions. Requires a send/activation API MoEngage does not expose today. Risk: high — reserve for the mature, proven subset only.

09

Manual-but-agentic operating model

This is the most important near-term section, because it's the model you can run today and because MoEngage forces manual publish regardless. The goal: strip nearly all strategic decision-making out of the operator's day. The operator becomes a builder, not a planner.

ClaudeEmits ranked Build Sheets
Each is a complete spec — nothing left to decide.
↓
OperatorBuilds in MoEngage from the sheet
Segment logic, content, schedule, control group, UTM — all copied field-for-field.
↓
OperatorTest-send & publish
Claude can trigger a test-send via MCP; operator eyeballs & publishes.
↓
ClaudeMeasures & writes the learning
Reads stats via MCP, compares to expected uplift, updates the Learning DB.

To make this near-zero-decision, the Build Sheet must map one-to-one onto the fields the operator sees while creating the campaign — the MoEngage Campaign Build Sheet (Section 10). Where possible Claude also pre-creates & validates the segment via MCP (which is reliable) and hands over its ID, so the operator doesn't rebuild audience logic by hand. That single step removes the most error-prone part of manual execution.

What agentic-but-manual buys you

Speed of experimentation and learning velocity rise sharply (the operator ships more, faster, consistently), while safety and reversibility stay maximal (a human still builds & publishes). It is the highest value-to-risk ratio available right now — and it's the natural home given the publish constraint.

12

Daily / weekly / monthly operating cadence

Every morning

Daily CRM Action Plan

Evaluate yesterday: revenue, CRM-attributed revenue, channel & campaign performance, anomalies. Scan opportunities: high-intent, lapsers, replenishment-due, cross-sell. Context: inventory, launches, promos, revenue-gap vs target. Output: ranked P1/P2/P3 interventions, each with WHO · WHY · WHAT · CHANNEL · WHEN · OFFER · EXPECTED IMPACT · EXECUTION (a Build Sheet). Then measure prior interventions.

Weekly

Portfolio & experiment review

Cohort migration (O1→O2 rates), channel mix & fatigue, experiment readouts & new hypotheses, calendar for launches/sales, incrementality vs control across the week, refresh RFM segments.

Monthly

Strategy & Constitution review

LTV & retention curves, discount-dependence trend, learning-DB consolidation into new rules, Constitution version bump, autonomy-ladder readiness check, roadmap re-plan.

Anti-pattern to avoid

Don't ask Claude to run the free-form analytics engine live each morning — it fails opaquely. Feed the daily brief from warehouse tables + the reliable MCP campaign/segment reads.

Operate here, now

Run at Autonomy Level 2 (Model B) today. Claude is the analyst, strategist and specifier; humans build and publish. This needs no engineering and captures most of the near-term revenue and learning-velocity upside at near-zero risk.

Conditions to move to Level 3

Advance to Claude-builds-drafts only when all hold: (1) a warehouse-backed intelligence layer is live and trusted; (2) Claude's impact estimates have a validated track record against control groups; (3) guardrail + brand-voice checks are automated and deterministic; (4) an approval queue with read-back diffing exists; (5) a template library is defined and each template has passed manual runs. Level 4+ requires months of clean Level-3 audit trail — and Level 5 additionally requires a send API MoEngage does not expose today.

Design once, climb forever: the intelligence layers (data → agents → decision engine → guardrails) never change as you raise permissions. Only the execution layer's access widens — which is exactly the property that lets you become more autonomous without redesigning the system each time.
